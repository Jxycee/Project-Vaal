## Claims I could NOT verify

- **Support-gem cap (2 → 5).** Stated twice and consistently in `docs/research/poe2/gems-and-skills.md`, but its cited sources are community wikis (Fextralife, gamers.wiki), and `docs/research/poe2/verified-corrections.md` contains **no** gem/socket entry — it was never re-verified against extracted game data the way the ascendancy cap was. Treat **5 as the cap** (it is the only number the repo has) but keep it a single named constant so a correction is a one-line change.
- **Number of active skill slots a character has.** `gems-and-skills.md:19` says "commonly cited as starting around 9, expanding with character level" — explicitly hedged. **So do not cap the number of loadouts**; a planner describes a target build, and inventing a cap from a hedged number is worse than having none.
- **Which supports are legal on which skill.** PoE2 gates supports by shared tags (`gems-and-skills.md:82`), but the index gives no compatibility relation and nothing in this repo models one. v1 offers all 616 supports unfiltered. Not a gap to paper over with a guess.
- **Max Spirit.** Not modelled anywhere in this repo; it comes from campaign progression and gear affixes. See the spirit-readout section.

## Where the spec is wrong

1. **"`'Spirit Gem'` identifies the reserving gems from the index."** False. `Spirit Gem` is the 39 **Meta** gems (all 39 carry the `Meta` tag); only 20 of them reserve. The other 89 of the 109 reserving gems are `Active Skill Gem` (59 — Heralds, Purities, Discipline, permanent minions) and `Support Gem` (30). Identifying reserving gems from the index alone is not possible.
2. **"Stored gem shape matches gear's: `{slug, name, category, iconUrl}`."** Gear's shape is `GearItem` = `{slug, name, category, isUnique, iconUrl}` (`gearSlots.ts`). Use `GearItem` unchanged — see Task 1.
3. **"`supports` capped at 5"** — correct as a number, but see "Claims I could NOT verify": it is community-sourced, not re-verified.
4. **Mobile: "Stacked cards, one per loadout slot, support gems wrapping within the card"** is fine but underspecifies the picker, which is the part the competitor recon says everyone gets wrong (`2026-09-20-competitor-build-planner-recon.md:85`). This plan reuses `ItemPickerSheet` — already a full-width single-column search-first list — rather than describing a new one.

## Architectural decision — extend `GET /api/wiki/items` with a kind dimension

**Decided: add gem pseudo-slots (`gem_skill`, `gem_support`) and make the route's slot→filter lookup return `{ kind, categories }`, then call `loadIndex(kind)`.** No new route, no new picker.

Why:

- `loadIndex(kind)` is **already** kind-generic and per-kind cached. The route's only item-specific line is `loadIndex('item')`. The change is ~8 lines.
- A sibling `/api/wiki/skills` route would duplicate the auth check, limit parsing, error mapping and the `filterEntries` call — about 60 lines, and two places to fix a ranking bug. That is exactly the "do not write a second search implementation" hazard the gear design already paid to avoid (`filterEntries.ts` exists precisely because of it).
- `ItemPickerSheet` already takes a `slot` prop and is already mounted two different ways (gear, jewels). Its header comment says "nothing here is gear-specific beyond the slot prop itself". A third mounting is the design working as intended.
- The pseudo-slot precedent is `JEWEL_PSEUDO_SLOT` — same trick, already shipped, already accepted by the route.
- **The route path stays `/api/wiki/items`.** It is a URL, not a type name. Renaming it touches three call sites for cosmetics and buys nothing; the header comment gets one line saying it now serves skill-kind pseudo-slots too.

**Consequence the implementer must not miss:** the route's auth check (`getCachedUser()` → 401) is the *only* thing gating this data, because `/api` is not in `PROTECTED_PREFIXES` while `/data/wiki/` is. Adding a kind dimension must not move, skip, or short-circuit that check.

## Global constraints (read before writing any code)

- **Mobile-first.** Unprefixed Tailwind must be a complete phone experience; `md:` adds desktop. Tap targets ≥ 44px (`h-11`) — `e2e/mobile-layout.spec.ts` measures this.
- **No new overlay position.** The Gems chip goes in the existing notice column's chip row. A sixth independently-positioned `absolute` overlay is what `mobile-layout.spec.ts`'s overlap check exists to fail.
- **Sheets portal to `document.body`.** `/tree`'s canvas wrapper is `position: fixed` and creates its own stacking context, so an in-place `fixed inset-0 z-40` sits under the shell's `sticky z-20` header. Copy `GearSheet`'s `createPortal` pattern verbatim.
- **Never import a pure function from a `'use client'` module into server code.** Next's RSC bundler turns every export of such a module into a client reference and throws at request time, while `type-check` and `build` stay silent. Gem slot/category constants go in a plain module.
- **`react-hooks` lint is strict** (`set-state-in-effect`, `preserve-manual-memoization`). Derive rather than setState-in-effect. **No `eslint-disable` (except the existing `@next/next/no-img-element` pattern for `/data/wiki/` icons), no `any`, no `@ts-expect-error`.**
- **Icons under `/data/wiki/` must use plain `<img>`, not `next/image`** — the optimizer's server-side fetch cannot carry the session cookie and gets redirected to `/login`. Copy the comment from `GearSheet`'s `SlotRow`.
- **Gates before every commit:** `npm run type-check` → `npm run lint` → `npm test` → `npm run build`. Report actual output, never expected.
- Do not run `npm install` (it silently reverts the `@poe2-toolkit` patch).

## Task 1 — `src/lib/build/gemSlots.ts`

- [ ] Create the module. Plain (no `'use client'`), because the API route imports it.

```ts
// src/lib/build/gemSlots.ts
// =============================================================================
// Gem pseudo-slot vocabulary and its skill-index category mapping.
//
// Gems live in the SKILL index, whose `category` vocabulary is disjoint from
// the item index's — which is why these are pseudo-slots carrying a wiki
// KIND as well as a category list (see GET /api/wiki/items'
// `filterForParam`). Same trick as gearSlots.ts's JEWEL_PSEUDO_SLOT, one
// level more general.
//
// Category strings verified against public/data/wiki/2026-08-25/skill-index
// .json on 2026-09-22: the only four values in that file are 'Active Skill
// Gem' (419), 'Support Gem' (616), 'Spirit Gem' (39) and 'Unused / Removed'
// (44). 'Unused / Removed' is cut content ([DNT-UNUSED] names) and is never
// offered.
// =============================================================================

/** A skill socket takes an active gem or a Meta/Spirit gem. */
export const GEM_SKILL_PSEUDO_SLOT = 'gem_skill';
/** A support socket takes a support gem. */
export const GEM_SUPPORT_PSEUDO_SLOT = 'gem_support';

export type GemPseudoSlot = typeof GEM_SKILL_PSEUDO_SLOT | typeof GEM_SUPPORT_PSEUDO_SLOT;

// 'Spirit Gem' is NOT "the gems that reserve Spirit" — all 39 of its entries
// carry the `Meta` tag (Cast on Shock, Blasphemy, …) and only 20 of them
// reserve anything, while 59 reserving gems sit under 'Active Skill Gem'.
// It is included here because Meta gems are socketed and supported exactly
// like active skills, not because of reservation. See this plan's "Where the
// spec is wrong" §1.
const GEM_SKILL_CATEGORIES = ['Active Skill Gem', 'Spirit Gem'] as const;
const GEM_SUPPORT_CATEGORIES = ['Support Gem'] as const;

export function isGemPseudoSlot(value: string): value is GemPseudoSlot {
  return value === GEM_SKILL_PSEUDO_SLOT || value === GEM_SUPPORT_PSEUDO_SLOT;
}

export function categoriesForGemSlot(slot: GemPseudoSlot): readonly string[] {
  return slot === GEM_SKILL_PSEUDO_SLOT ? GEM_SKILL_CATEGORIES : GEM_SUPPORT_CATEGORIES;
}

/**
 * Support sockets per skill: starts at 2, maxes at 5 (1 active + 5 supports
 * = the classic six-link, entirely local to the skill).
 *
 * Sourced from docs/research/poe2/gems-and-skills.md §1 and §4, which agree
 * — but that doc's citations are community wikis and
 * docs/research/poe2/verified-corrections.md never re-verified this against
 * extracted game data the way it did the ascendancy cap. Kept as one named
 * constant so a correction is a one-line change.
 */
export const MAX_SUPPORTS_PER_SKILL = 5;
```

- [ ] `src/lib/build/__tests__/gemSlots.test.ts`: read the real index off disk with `node:fs` and assert (a) the distinct `category` set is exactly those four strings, (b) every category this module maps to has a non-zero entry count, (c) no mapped category has zero entries. A resync that renames a category must fail here, not ship a silently empty picker — this is the `Focus`/`Focii` lesson applied before the fact.

## Task 2 — `src/lib/build/gemState.ts`

- [ ] Create the module. Pure; no React, no fetch. This is the real unit-test target.

**Stored shape — `GearItem` reused byte-for-byte**, as jewels already do. Verified: every skill-index entry has `isUniqueItem: false`, so `isUnique` is dead weight on a gem — but reusing `GearItem` means `ItemPickerSheet`'s `onPick` needs no mapper and `isGearItem` is the validator, both already tested. A parallel near-identical type is the cost side, and it is bigger.

```ts
import type { WeaponSet } from '@poe2-toolkit/tree-core';
import { isGearItem } from './gearState'; // already exported and already unit-tested
import type { GearItem } from './gearSlots';
import { MAX_SUPPORTS_PER_SKILL } from './gemSlots';

export interface GemLoadout {
  /** Stable, client-generated. Identity has to survive reordering and removal, so it cannot be the array index. */
  id: string;
  skill: GearItem | null;
  /** At most MAX_SUPPORTS_PER_SKILL. */
  supports: GearItem[];
  /**
   * Weapon sets this loadout is active in. `[1, 2]` means "both", spelled
   * the same way passive_state spells an untagged node (present in both
   * set1 and set2) — one vocabulary, not two.
   */
  sets: WeaponSet[];
}

export interface GemState {
  loadouts: GemLoadout[];
  /** Which loadout's skill populates builds.main_skill. Null until one is set. */
  primaryId: string | null;
}
```

- [ ] `emptyGemState(): GemState` → `{ loadouts: [], primaryId: null }`.
- [ ] `newLoadout(): GemLoadout` → `{ id: newLoadoutId(), skill: null, supports: [], sets: [1, 2] }`. Keep `newLoadoutId()` a separate non-exported-from-pure-tests concern: `` `${Date.now().toString(36)}-${Math.random().toString(36).slice(2, 8)}` ``. Do **not** use `crypto.randomUUID()` — it is undefined on insecure origins, and this runs in the browser.
- [ ] `parseGemState(raw: unknown): GemState` — defensive, exactly like `parseGearState`:
  - non-object / array / null → `emptyGemState()`;
  - `loadouts` not an array → `[]`;
  - per loadout: drop it entirely only if `id` is not a non-empty string; otherwise `skill` falls back to `null` unless `isGearItem`, `supports` filters to `isGearItem` entries and **truncates to `MAX_SUPPORTS_PER_SKILL`**, `sets` filters to `1`/`2`, dedupes, sorts, and falls back to `[1, 2]` when empty;
  - `primaryId` kept only if it matches a surviving loadout's id, else `null`.
  - One malformed loadout must not blank the others (the `parseGearState` rule).
- [ ] Pure reducers, all `(state, …) => GemState`, none mutating: `addLoadout`, `removeLoadout(id)` (also clears `primaryId` when it pointed there), `setSkill(id, item|null)`, `addSupport(id, item)` (**no-op at the cap**), `removeSupport(id, index)`, `setSets(id, sets)`, `setPrimary(id)`.
- [ ] `deriveMainSkill(state: GemState): string | null` — the primary loadout's `skill.name`; if `primaryId` is null or that loadout has no skill, fall back to the **first** loadout that has a skill; else `null`. Pure, and the single definition of what `builds.main_skill` means.

- [ ] `src/lib/build/__tests__/gemState.test.ts` covers: every `parseGemState` fallback above (including a `supports` array of 8 truncating to 5 and a dangling `primaryId` clearing); `addSupport` at the cap being a no-op that returns an equal state; `removeLoadout` clearing a matching `primaryId`; `setSets` normalising `[2,2,1]` → `[1,2]` and `[]` → `[1,2]`; all three `deriveMainSkill` branches.

## Task 3 — Route: add the kind dimension

- [ ] In `src/app/api/wiki/items/route.ts`, replace `categoriesForParam` and the `loadIndex('item')` call:

```ts
import type { WikiEntryKind } from '@/lib/wiki/types';
import { categoriesForGemSlot, isGemPseudoSlot } from '@/lib/build/gemSlots';

/**
 * `slot` covers the 17 gear slots, the `jewels` pseudo-slot, and the two gem
 * pseudo-slots. Gems live in the SKILL index, whose category vocabulary is
 * disjoint from the item index's — hence a kind alongside the categories.
 * Returns `null` for anything else so the caller can 400 rather than let an
 * arbitrary category string reach the filter.
 */
function filterForParam(slot: string): { kind: WikiEntryKind; categories: readonly string[] } | null {
  if (isGemPseudoSlot(slot)) return { kind: 'skill', categories: categoriesForGemSlot(slot) };
  if (slot === JEWEL_PSEUDO_SLOT) return { kind: 'item', categories: JEWEL_CATEGORIES };
  if (isGearSlot(slot)) return { kind: 'item', categories: categoriesForSlot(slot) };
  return null;
}
```

- [ ] Downstream: `const filter = filterForParam(slotParam)` → 400 on null; `index = await loadIndex(filter.kind)`; `index.filter((e) => filter.categories.includes(e.category))`.
- [ ] Leave the `getCachedUser()` 401 check exactly where it is, first. Extend the file header comment to say the route now serves skill-kind pseudo-slots, and why the path keeps its name.
- [ ] Nothing else changes: `filterEntries` already searches `['name','category','tags']`, and skill entries have real `tags` (verified: 0 of 1,118 missing), so tag search ("fire", "minion", "projectile") works on gems for free.

## Task 8 — Spirit reservation readout: **out of v1**

Recommendation: **do not build it.** The spec already calls it explicitly optional; the verified data says it is more expensive and less correct than the spec assumed.

- The spec's cheap path does not exist. `'Spirit Gem'` is the **Meta** category, not the reserving set: 109 gems have a reservation, split 59 `Active Skill Gem` / 30 `Support Gem` / 20 `Spirit Gem`. There is no index-only predicate for "reserves Spirit".
- **No client-side typed detail fetcher exists.** `fetchWikiCardSnippet` is the only client-side detail reader and its `extractCardSnippet` returns `{iconUrl, iconWidth, iconHeight, snippet, accent}` — it drops `scaling` entirely. A readout needs a new typed fetcher plus one `/data/wiki/<v>/skills/<slug>.json` request per gem in the build, on a phone, for every loadout render.
- It would be wrong for 9 gems. Reservation is level-invariant for 100 of the 109, but the 9 skeleton minion gems scale it hard (Skeletal Brute 165 → 58 across levels) and this planner does not model gem level.
- It has no denominator. Max Spirit comes from campaign progression and gear affixes (`gems-and-skills.md` §5); nothing in this repo models it. "72 Spirit reserved" out of an unknown pool is a number, not information.

If it is ever picked up: the fields are `scaling[].reservation` on the skill detail, `gemType` is `'spirit' | 'active' | 'support'` on the detail (41/455/622 — and it does **not** agree with the index `category` counts, so do not substitute one for the other), and the cheapest correct shape is a server route that resolves reservations for a list of slugs in one request rather than N client fetches.
