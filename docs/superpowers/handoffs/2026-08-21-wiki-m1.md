### 1. AGENTS.md's GGG-art guardrail — written

**Resolution:** GGG art was never meant to be a reference/template for original Project Vaal assets, but authentic GGG artwork IS required for depicting real in-game content (tree, wiki item/gem/skill icons) — a lookalike substitute would be wrong. Written into `AGENTS.md` (commit `3ce70993`), naming the tree and wiki icons as the two scoped exceptions, both sourced only via the official `@poe2-toolkit` patch-server data.

### 2. Product plan doc — skipped, by direction

**Resolution:** Jaycee said not to worry about it; will ask for changes if needed. No action taken, none planned.

### 3. `/data/wiki/**` — gated, plus the browse-page cleanup this unblocked

**Resolution:** Data must be gated too; signed-out users should not be able to use the wiki at all. Implemented in three rounds (commits `e0c5fc62`, `bd524cf6`, `6377f997`, `cdeaa326`), each independently reviewed against compiled build artifacts, not just source:

- `src/proxy.ts`'s middleware matcher now lets `/data/wiki/**` through (narrowed from a blanket `data/` exclusion to `data/tree/` only, preserving the tree's existing public/fast behavior unchanged) and `/data/wiki` was added to `PROTECTED_PREFIXES`.
- **Two real bypasses were found and fixed along the way**, both by independent reviewers tracing the actual compiled `.next` artifacts rather than trusting source: a percent-encoding bypass of `isProtectedPath` (`/data/%77iki/...` would reach the real file without triggering the redirect), and a cache-header rule that kept granting `public`/`immutable` caching to gated content for any percent-encoded spelling of a wiki path — both closed, both re-verified against fresh builds.
- Also fixed: service worker runtime-caching of gated data (now `NetworkOnly` for `/data/wiki/`, plus a one-time `activate`-time cleanup of anything an older SW version cached), and the previously-deferred **Important finding #8** — browse pages (`/wiki/items`, `/wiki/skills`, `/wiki/mods`) now fetch the search index client-side (`fetchWikiIndex()` + a new `WikiBrowse` wrapper) instead of re-parsing it server-side on every request.
- Documented, not fixed (a real architecture note, not a bug): `src/proxy.ts` now has a comment stating proxy-level middleware auth isn't full defense-in-depth per Next's own docs — `AppShell` reads the session but doesn't itself redirect. A durable fix would mean serving wiki data through a Route Handler with its own `getUser()` call instead of raw static file serving; out of scope for this round, flagged for awareness.

Final independent review verdict: **Ready to merge.** Two honestly-flagged residuals remain, non-blocking: no integration/route-level test harness exists in this repo to assert the redirect behavior end-to-end (only compiled-artifact tracing + unit tests were used across all three rounds), and no live dev-server click-through was performed in this sandboxed environment. Both are reasonable post-merge follow-ups, not blockers — see `docs/superpowers/handoffs/wiki-data-gating-report.md` for full detail on all three rounds.

## Known, accepted residual (non-blocking)

`resetIconRoot()` in `scripts/sync-wiki.ts` wipes the whole icon tree once, up front, before any of the three kinds' truncation guards run. If a future sync's `syncItems` or `syncSkills` step (not just `syncMods`) trips the guard and throws, the icons are already gone but the old JSON isn't — a locally broken intermediate state. Doesn't reach production (a failed sync step blocks the CI workflow's PR-creation step), recoverable locally via `git checkout -- public/data/wiki`. Worth a follow-up before the guard fires in anger for real.

## Real bugs found and fixed along the way (not scope changes, just noting for context)

- `WIKI_PATCH_VERSION` was stale on arrival in Task 1 (404'd against the live CDN) — fixed via a live patch-server handshake, documented in the recon doc.
- The truncation guard (`previousCount`/`findPreviousVersionDir`) was inert in its original form — inherited from my own plan's sample code, not an implementer mistake — fixed twice (once at task-review, once more thoroughly at final review) and now has live confirmation it actually fires.
- Real gem-name slug collisions (Herald of Ash/Ice/Thunder, per-weapon default attacks, 45 unreleased "Coming Soon" placeholders) needed a `dedupeSlug` helper not in the original plan.
- 13,354 of 16,679 raw mod entries had no display name (internal ids like `UniqueAttackCriticalStrikeChance1UNUSED`) — filtered.
- Icons: full-resolution (up to 512×1024, 759KB) served in a 48px box — downscaled to ≤128px, cut icon payload from 184.5MB to ~36MB.
- Service worker was precaching all 27,771 wiki data files (211MB) for every visitor to any page — excluded.
- 211MB was being traced into each of the three detail-page serverless functions — icon downscale fixes the actual deploy-blocking size regardless of platform; the `next.config.ts` trace-excludes are additionally correct but unverifiable from this Windows machine (confirmed via direct picomatch testing) and will only show their full effect on a real Vercel/Linux build.
