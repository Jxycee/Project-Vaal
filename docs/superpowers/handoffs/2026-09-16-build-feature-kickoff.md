# Build Feature Kickoff — Handoff for Local Claude Code

**Status:** No code written yet. This is a task handoff, not a session recap — it hands off Tasks 1-4 below to whoever picks this up next. Everything in it was verified against the actual repo source and a same-day PoE2 research pass, not assumed from the planning docs alone (the planning docs describe intent that, in a few places, drifted from what's actually in `main` — see "Verified current state" below).

## Why this doc exists

Project Vaal has zero "build sharing" functionality on the frontend. It's the single biggest gap on the site relative to what the login page's own tagline promises ("Price checks, passive-tree planning, campaign tracking, and build tools"). The DB schema for it has existed since `supabase/schema.sql` was written; nobody has built the UI on top of it. This doc scopes exactly the four pieces needed to close that gap, in dependency order — nothing past #4 (import formats, live character sync) is worth touching until these four exist, because those are just alternate ways of filling the same editor.

## Read first: game-mechanics reference

`docs/research/poe2/` is a same-day research set (17 files + `README.md` + `CHEATSHEET.md`) covering Path of Exile 2 end to end, gathered specifically because this repo's own PoE2 knowledge (comments, plan docs) predates several patches. **Read `docs/research/poe2/CHEATSHEET.md` first** — it's one page and links to everything else. The files that actually matter for Tasks 1-4:

- `docs/research/poe2/classes-and-ascendancies.md` + `verified-corrections.md §1` — 8 live classes (Warrior, Ranger, Monk, Sorceress, Mercenary, Witch, Huntress, Druid), 22 ascendancies, **8-point ascendancy cap** (2 points per Trial of Sekhemas/Chaos completion, up to 4 completions) — use this to validate ascendancy-point spend in the build editor, don't invent a number.
- `docs/research/poe2/gems-and-skills.md` — the gem/socket model (2-5 support slots per skill via Uncut Gems, no item-socket gems), the **Spirit** resource (separate reservation pool for Persistent-tagged skills — auras/minions/banners), all 6 ailments. Relevant to the gem-loadout UI in Task 3 (a Spirit-reservation readout is the kind of thing a real build planner shows).
- `docs/research/poe2/items-and-crafting.md` — confirms **2 flask slots + 3 charm slots** as the current consumable-slot count (not PoE1's flask belt), and that there are no gear sockets/links in the PoE1 sense (Runes/Soul Cores are separate items, not socketed gems) — matters for designing `gear_state`'s slot keys in Task 2.
- `docs/research/poe2/build-sharing-ecosystem.md` + `verified-corrections.md §4` — the PoB2 share-code format and GGG's official `.build` JSON schema. Not needed for Tasks 1-4 directly, but the `passive_state` shape already in `supabase/schema.sql` was deliberately designed to line up with GGG's own `.build` weapon-set convention (see below) — skim this now so Task 2/3's `gear_state`/`gem_state` shapes don't paint you into a corner before that compatibility work happens later.
- `docs/research/poe2/patch-history-and-meta.md` — current patch is **0.5.5 "Forbidden Rites"** (on base 0.5.0), 1.0 targeted 2026-12-11. Relevant to the `game_version` column (see gap below).

If anything in the existing plan docs (`docs/superpowers/plans/*.md`) or code comments states a PoE2 fact that conflicts with the research set, **the research set is newer — trust it**, and flag the conflict rather than silently picking one.

## Verified current state (read the source, not just the plans)

Checked directly against `main` this session:

- **Tree viewer (M1) is done** at `/tree` (`src/app/(dashboard)/tree/page.tsx`, `src/components/tree/PassiveTree.tsx`). It's a good reference for interaction patterns (touch-vs-desktop allocation, weapon-set tagging) but **has no persistence at all** — not localStorage, not server. Refresh loses everything. Grepped the whole `src/` tree for `localStorage`/`sessionStorage`: the only hits are in `src/lib/wiki/` (recent-searches, a session-scoped view-mode cache). The original M1 plan's checkpoint ("refresh restores state") was never actually implemented, or was reverted — don't assume a localStorage layer exists to build on top of. Task 1 is adding persistence *and* a server save in one move, not upgrading an existing local layer.
- **`PassiveTree.tsx`'s in-memory state is exactly what Task 1 needs to lift into `builds.passive_state`**: `main: WeaponSetAllocation` (`{ allocated: number[], weaponSets: Record<number, 1|2> }`) plus a separate `ascendancyNodes: number[]`. The schema's own `passive_state` shape (`{ set1, set2, ascendancyNodes }`) is a different encoding of the same three facts — `weaponSets` tags 1/2/untagged per node, `set1`/`set2` are two explicit id arrays with "in both" meaning untagged/shared. Pick one encoding and convert at the boundary; don't run two representations through the app.
- **`characters` table exists but is empty and has no creation UI** (confirmed by a comment in `schema.sql` itself: "the character system isn't built yet (0 rows in `characters`, no creation UI)"). `builds.character_id` is nullable specifically so standalone builds work today. **Build Tasks 1-4 with `character_id` always NULL** — don't build character-linking UI now, it's a separate, unscoped feature.
- **`ladder_entries` table and `user_profiles.ggg_*` OAuth token columns exist in the schema but nothing reads/writes them** — no `/api/ladder/sync` route, no OAuth callback route, no GGG API client anywhere in `src/`. This is forward-planning-only. Don't treat GGG API integration as "half-done" — it's 0% done. (Irrelevant to Tasks 1-4, but don't get confused by the schema comments implying otherwise.)
- **Only one API route exists at all**: `src/app/api/prices/sync/route.ts`. There's no existing pattern in this repo for a *user-triggered* (not cron) write route — Task 1's save endpoint will be the first of its kind. Follow `src/lib/supabase/server.ts`'s `createClient()` pattern (cookie-based, RLS-respecting — do NOT use `createServiceClient()` for user saves, that bypasses RLS and is reserved for cron/admin per its own doc comment).
- **`nanoid` is already a dependency** (`^5.1.11`) — matches the schema comment "share_token: 21-char nanoid; generated server-side on first save." Use it directly, don't add a new ID library.
- **`increment_build_view_count(uuid)` RPC already exists and is already granted to `anon, authenticated`** — Task 4's public build view just needs to call it (`supabase.rpc('increment_build_view_count', { p_build_id })`), nothing to add server-side for view counting.
- **`build_tags` and `build_bookmarks` tables and their RLS policies are complete** — Task 4's finder/bookmark UI has no schema work left, only frontend.
- **The tree's own vendored data is `0.5.2`** (`TREE_VERSION`/`ASSET_VERSION` in `PassiveTree.tsx` and `tree/page.tsx`), while the current live patch is **0.5.5** per the research set. Worth a quick check (not blocking Task 1-4, but do it before or during Task 1 since `passive_state` node ids are only meaningful relative to a specific tree export version): has GGG's `poe2-skilltree-export` repo published newer node data since 0.5.2? If node ids shifted, `game_version`-stamping a build (see next point) is what makes a future re-sync safe rather than silently corrupting old saves.
- **`builds.game_version` defaults to `'0.2.0'`** — three-and-a-half patches stale relative to current `0.5.5`. Fix the default (or better, stop relying on the column default and always pass the actual current version explicitly from a single constant at save time — see `TREE_VERSION`/`WIKI_PATCH_VERSION`-style constants elsewhere in the codebase for the existing pattern of hand-bumped version constants).
- **No slot taxonomy exists for gear** — `WikiItemDetail` (`src/lib/wiki/types.ts`) has `itemClass`/`category` (free-text, ~90 real values) but nothing shaped like an equipment slot. `src/lib/wiki/categoryTaxonomy.ts`'s `ITEM_CATEGORY_GROUPS` (Armour/Weapons/Jewellery/Flasks/etc.) is the closest existing thing — reuse it to *filter* the item picker per slot (e.g. the Ring slot's picker searches within the `Jewellery` group's `Ring` category), but you still need to hand-write the slot list itself (see Task 2).
- Interesting, non-blocking: `ITEM_CATEGORY_GROUPS`'s `Currency` group lists a `DivinationCard` category. The research set (`docs/research/poe2/monsters-and-loot.md`) independently confirmed PoE2 has **no live Divination Cards** — this is very likely the same phenomenon `verified-corrections.md`'s Incursion investigation found in GGG's raw data (dead/legacy categories ship in the client's data tables even for absent mechanics). Not a bug to fix here, just don't be surprised if a `DivinationCard`-tagged item shows up somewhere and don't build gameplay logic assuming cards are collectible.

## Task 1 — Save-to-Build

Wire the existing tree editor's in-memory allocation into `public.builds`.

- New route (Route Handler, not a Server Action, so it's reusable if a future non-web client needs it — but either is defensible, use your judgment) that does an authenticated upsert into `builds`, using `createClient()` (cookie-scoped, RLS-respecting).
- On first save: generate `share_token` via `nanoid()` (21 chars, matches schema comment), leave `is_public` false by default (owner has to explicitly publish — see Task 4's finder, which should only ever list `is_public = true` rows, already enforced by the `builds_public_idx` partial index and RLS policy).
- Convert `PassiveTree.tsx`'s `{ main: WeaponSetAllocation, ascendancyNodes }` into the schema's `passive_state: { set1, set2, ascendancyNodes }` shape at the save boundary (see "Verified current state" above for the exact mapping). Write this conversion as a small pure function with a unit test (this repo TDDs its `src/lib/tree/` logic already — `src/lib/tree/__tests__/` is the pattern to follow) rather than inlining it in a component.
- Stamp `game_version` from an explicit constant, not the column default.
- Add basic persistence for the *unsaved, in-progress* editor state too (a real gap right now — see above) — a simple localStorage draft keyed by class/ascendancy is enough; it does not need to be the server save itself, just something so a refresh mid-edit doesn't nuke a user's in-progress allocation before they've saved.
- Ascendancy-point validation: 8-point cap total, 2 per trial completion (`classes-and-ascendancies.md`) — decide whether the editor enforces this client-side (recommended — cheap sanity check, and the tree's own `toggleAscendancyAllocation` may already gate this at the graph level; confirm before adding a second check that could disagree with it).

## Task 2 — Gear/equipment slot UI

- Design the slot key set for `gear_state` explicitly — the schema comment only sketches `{ head, body, ... }`. Based on `items-and-crafting.md`: head, body, gloves, boots, amulet, ring1, ring2, belt, weapon1_main, weapon1_off, weapon2_main, weapon2_off (two full weapon sets, matching the tree's own set1/set2 concept — same weapon-set duality, keep the naming consistent with whatever Task 1 settles on for `passive_state`), plus flask1-2 (2 flask slots) and charm1-3 (3 charm slots). Confirm the exact flask/charm counts against `docs/research/poe2/items-and-crafting.md` before hardcoding — that doc flags its own numbers as WebSearch-sourced, not GitHub-verified, in a couple of spots.
- Each slot picker searches the existing wiki item index (`src/lib/wiki/fetchIndex.ts` / `WikiSearchEntry`), filtered to the relevant `ITEM_CATEGORY_GROUPS` categories for that slot (e.g. `head` → `Helmet` from the `Armour` group). Selecting an entry should store enough of `WikiItemDetail` in `gear_state` to render the slot without a live fetch on every build view — decide the exact subset (name, icon, rarity, category at minimum) as part of this task, don't store the entire detail object if it's mostly redundant with a wiki lookup by slug.
- No item-socket/link UI needed — PoE2 has no gear sockets in the PoE1 sense (confirmed, `items-and-crafting.md` + `verified-corrections.md §2`). Don't build a socket-linking interaction; Runes/Soul Cores (if you support them at all in v1) are their own item picks, not sub-slots of a weapon.

## Task 3 — Skill/gem loadout UI

- `gem_state`'s schema comment sketches `{ slots: [{ skill: {...}, supports: [{...}] }] }` — a skill gem plus 0-5 support gems per slot (2-5 support slots per skill is the current mechanical range, per `gems-and-skills.md`; don't hardcode exactly 5 as a floor).
- Source gem options from the wiki's skill index (same `fetchIndex`/`WikiSearchEntry` pattern as Task 2, filtered to `kind: 'skill'`). `src/lib/wiki/__fixtures__/sample-gem.json` is a concrete real-shape example to check against while wiring this up.
- Tag each loadout slot to a weapon set (1/2/both), same convention Task 1 uses for the tree — this is a design decision already made at the tree level (`docs/superpowers/plans/2026-07-06-passive-tree-milestone-1.md`: "Weapon set = per-node tagging... matching GGG's `.build` format"); carry the same red/green/gold-style set tagging into the gem UI instead of inventing a different mechanism.
- Consider a Spirit-reservation readout (sum of allocated Persistent-tagged skills' Spirit cost vs. available Spirit) — not required for v1, but cheap to add if the wiki's skill data exposes a Spirit-cost field, and it's the kind of thing that makes this feel like a real build planner rather than a form. Check `WikiItemDetail.spirit` (exists on items, per `src/lib/wiki/types.ts`) and the skill-side equivalent before committing to this — verify the field actually exists on skill entries, don't assume it mirrors the item shape.

## Task 4 — Build finder + public build view + share route

- New routes: a `/builds` finder (list `is_public = true` builds, filterable by `class`/`league` — both already indexed via `builds_public_idx`; add tag filtering via `build_tags`), and a public build detail route. The PWA plan (`docs/superpowers/plans/2026-07-12-pwa-serwist.md`) already anticipated the URL shape: **`/builds/[shareToken]`** — use that path, it's already referenced elsewhere as the expected convention (a stale `/tree/[shareToken]` redirect comment references it).
- Public detail route: fetch by `share_token`, call `increment_build_view_count` RPC once per view (already exists, already granted — see above), render the tree/gear/gems read-only using the same rendering components Tasks 1-3 build (don't fork a second renderer for "view mode" — pass a read-only flag through the same components).
- Bookmarking: `build_bookmarks` table + RLS is complete; just needs a button wired to insert/delete for the signed-in user.
- Tag input for the owner's own build (`build_tags`, freeform, 1-32 chars per the CHECK constraint) — simple add/remove chip UI, no schema work.
